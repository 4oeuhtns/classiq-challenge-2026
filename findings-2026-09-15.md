# Session Findings — 2026-09-15: Chasing the Leaderboard (137 depth / 561 CX)

*A companion to `plan.md`, not a replacement. Written for someone new to both quantum
circuits and this project. Where a claim can be checked by running code, it already
has been — every number below came from a real transpile or a real linear-algebra
calculation, not a guess.*

---

## 0. The one-paragraph summary

Starting point: our best working circuit (`experiments/handbuilt.py`) scores
**depth 1906, CX 1251**. The leaderboard's best public score is **depth 137, CX 561**.
Today's goal was to close that gap. It wasn't closed. But several real, different
circuit designs were built and measured (not estimated) trying to close it, two more
ideas raised mid-session were tested the same way, and each failure taught something
specific about *why* the gap exists. That diagnosis — plus one concrete,
already-recommended, never-actually-tried tool — is what this document is for.

---

## 1. Recap: what "depth" means, and the mental model that was wrong

`plan.md` Part II already covers the basics (a phase oracle is a reversible Boolean
circuit; XOR combines regions; ancillas must return to zero). This session forced a
correction to one assumption everyone — including this project's own earlier
experiments — was making without saying it out loud:

> **Two gates that merely *read* the same qubit — as a yes/no condition, not even
> writing to it — still cannot happen at the same moment.**

Depth is counted in **layers**. A qubit can appear in at most one gate per layer,
full stop. It does not matter whether the two gates "logically commute" (would give
the same answer in either order) — if they both need to touch qubit `y4` in the same
step, one of them has to wait. Physically this is like a single-lane bridge: two cars
can cross it in either order, and neither damages the other, but they still cannot be
*on the bridge at the same instant*. Being "read-only" doesn't create a second lane.

This matters because most of today's failed attempts assumed that giving two pieces
of logic *separate scratch qubits* would let them run side by side. It doesn't, if
they both still need to read, say, the same bit of `x` or `y` — and it turns out our
designs read the same handful of coordinate bits constantly.

---

## 2. Finding 1 — our circuit's 10 building blocks are already the mathematical minimum for this style of construction

`handbuilt.py`'s design works by picking 10 "pieces." Each piece says: *for this set
of rows (y-values), stamp this set of columns (x-values)*. The 10 pieces are XORed
together (stamped twice = erased, per `plan.md` II.4).

This kind of "row-pattern times column-pattern, summed together" construction has a
name in linear algebra: it's a **rank decomposition** of the 64×64 grid of black/white
pixels, done over the two-element number system (everything is 0 or 1, and addition
wraps around — this is called **GF(2)**, and it is exactly the arithmetic that makes
XOR "addition"). The **rank** of a grid, in this system, is the fewest number of
row-pattern/column-pattern pairs needed to reconstruct it exactly.

Today this rank was computed directly (ordinary Gaussian elimination, adapted to
wraparound arithmetic) instead of estimated. Result:

**The true rank of the logo's pixel grid is exactly 10.**

That matches the number of pieces already in use. In plain terms: *if your strategy
is "sum of row-pattern times column-pattern terms," 10 terms is not a guess someone
made — it is provably the fewest possible.* No amount of re-searching for a better
9-piece or 8-piece version of this style of circuit will succeed, because it doesn't
exist. Future effort should stop trying to shrink the *number* of pieces and instead
attack *how expensive each piece is*, or abandon this style of construction
altogether (see §12).

---

## 3. Finding 2 — fewer/cleaner pieces is not the same as a cheaper circuit

Having proven 10 is minimal, the natural next idea was: build those 10 pieces the
"obvious" way — one piece per real shape (square, bar, each disk split into its
natural rings) — instead of whatever oddly-shaped pieces a search algorithm found.
This gives very clean, easy-to-understand pieces (verified pixel-for-pixel correct).

Measured result: **depth 2165, CX 1413** — *worse* than the existing 1906/1251.

This isn't a contradiction; it lines up with something `plan.md` already flagged back
on 2026-09-13 (Part II.5 and Phase 2):

> A rectangle's cost depends on **where its edges land**, not on how simple the
> rectangle looks. `plan.md` measured the *same shape* costing **398 depth** with
> arbitrary edges and **47 depth** with edges snapped to a power of two — an 8.5x
> difference from alignment alone.

The clean, "natural shape" pieces have boundaries at ordinary pixel coordinates (2,
26, 27, 48, etc.), which are *not* aligned to powers of two. Building a circuit
condition for "x is between 2 and 26" costs more gates than "x is between 0 and 31,"
even though the second range is bigger, because of how the bit-pattern math works.
**Simplicity to a human eye and cheapness to the circuit are different properties.**

---

## 4. Finding 3 — the existing 10-piece design is already sitting in a valley

Any valid rank-10 decomposition can be turned into a *different, equally valid*
rank-10 decomposition using two simple, provably-safe moves (swap information between
two pieces' row-patterns, or between two pieces' column-patterns — this is just
Gaussian elimination in reverse, so correctness can never break). A search was run
that tried tens of thousands of such moves, starting from the current best design, to
see if a cheaper-but-still-correct rearrangement exists.

Result: the cost barely moved (2169 → 2167), and it landed in the exact same place
from six different random starting points. That's a strong signal the current design
already sits in a genuine local optimum for this move set — not a lucky first guess
that a bit more shuffling would beat.

---

## 5. Finding 4 — a clever trick ("dirty" scratch qubits) that works correctly but doesn't help here

**The idea, in plain terms:** normally, a scratch qubit ("ancilla") must be reset to
empty (state `|0⟩`) before it can be borrowed for a new calculation — like erasing a
whiteboard before writing new notes on it. There's a known technique (built into
`qiskit`, verified independently today) that skips the eraser: it borrows a scratch
qubit **in whatever state it's already in** — even mid-calculation, even entangled
with other qubits — does its work, and is *mathematically guaranteed* to hand it back
in exactly the state it found it. It's like borrowing a colleague's desk chair while
they're at lunch: you don't need to know or care what was already on the seat, as
long as you put it back exactly as found.

This was tested rigorously — not just "does it give the right answer for input 0" but
a full check that the *entire* mathematical description of the gate (including the
invisible global-phase bookkeeping) matches, for a scratch qubit left in a totally
arbitrary/random state. It passed. The idea was sound: with this trick, the hope was
to run 2-3 independent pieces of the circuit at once, each with its own small,
`dirty`-ancilla-based bundle of logic, instead of funneling everything through one
shared scratch pool.

**Result: no improvement (depth ended up worse, ~6000+).** Building three separate
mini-circuits and giving each its own scratch space didn't help, because — per the
bridge analogy in §1 — the three "independent" pieces all still needed to read from
the *same* 12 coordinate wires very often. Splitting the scratch didn't remove the
actual traffic jam; it just moved where it happened.

---

## 6. Finding 5 — finding the actual traffic jam, by measurement

Rather than guess where the bottleneck was, the transpiled circuit was inspected
directly: for every one of the 18 wires, how many gates touch it?

**In the current best (1906-depth) design:**

| Wire | Gate-touches |
|---|---:|
| ancilla `a3` | **855** |
| ancilla `a2` | 767 |
| ancilla `a4` | 636 |
| *(all 12 coordinate wires)* | 27–113 each |

One single scratch qubit is touched 855 times — nearly half the entire circuit's
depth traces back to that one wire being needed, over and over, by many different
pieces sharing the same small scratch pool. The 12 coordinate wires, by contrast, are
barely used (at most 113 touches). **This is the real bottleneck in the current
design: too many pieces fighting over too little scratch, not the coordinate logic
itself.**

**In the "dirty ancilla, 3 pipelines" attempt from §5, the picture flips:**

| Wire | Gate-touches |
|---|---:|
| `y4` | **1815** |
| `y5` | 1553 |
| `y2` | 1320 |
| ancillas | 533–695 each |

Freeing up the scratch qubits worked — but it exposed that the coordinate wires
(especially the highest two bits of `y`, which every range check needs to look at
first) are read constantly across almost every piece. The traffic jam didn't
disappear; it moved from the ancilla onto the coordinate wires.

**The lesson:** the current architecture has *two* bottleneck resources — the shared
scratch pool, and the shared coordinate wires — and relieving one exposes the other.
A real fix has to relieve both at once, which likely means a different circuit shape
altogether (see §12), not a reshuffling of the current one.

---

## 7. Finding 6 — trying to fix the traffic jam by spreading the load out evenly makes things *worse*, and the reason is worth knowing before trying it again

Finding 5 found one scratch qubit doing far more work (855 touches) than another
(178). The obvious next idea: make a rule that always hands the *next* piece of work
to whichever scratch qubit has done the *least* work so far — a direct, "keep it
balanced" fix, close in spirit to load-balancing or register allocation. A coarser
version of the same idea was also tried: instead of rebalancing constantly, just
rotate which scratch qubit each of the 10 pieces starts from, so no single wire is
everyone's first choice.

Both were built and measured. Both worked exactly as intended at the one thing they
were designed to do — the busiest wire dropped from 855 touches down to roughly
600–750, and the wires ended up close to evenly loaded.

**And both made the final result worse: depth 1986 (was 1906) for the constant
rebalancing, depth 2043 for the per-piece rotation.**

This is a genuinely useful, slightly counter-intuitive finding, and it was tracked
down rather than left as a mystery. The *raw* circuit — before Qiskit's own automatic
clean-up step runs — is **identical in every version**: same 590 three-way-controlled
gates, same 366 single-qubit flips, same 574-layer starting depth, no matter which
scratch-assignment rule was used. The difference only shows up *after* the automatic
clean-up runs, and it gets bigger the more aggressively that clean-up is allowed to
work (checked at three clean-up strengths: with clean-up switched off, all versions
tie exactly at 1803 two-qubit gates; at full strength, the original wins 1251 to
1366–1369).

**Plain-language explanation:** Qiskit's clean-up step is good at spotting *repeated*
patterns — for instance, an operation immediately followed by something that
undoes it, which can simply be deleted, the same way "add 3, then subtract 3" is the
same as doing nothing. The original design, by always reaching for the same scratch
qubit first every time, *accidentally* creates a lot of these repeatable patterns,
which the clean-up step is very good at finding and removing. Deliberately spreading
work out evenly is, in effect, deliberately making every occurrence a little
different from the last one — which is exactly what stops the clean-up step from
recognizing them as repeats. The balancing succeeded at its own goal and lost more to
broken clean-up than it gained from being balanced.

**Lesson for next time:** load-balancing the ancilla is still the right instinct in
general — but in this toolchain it needs to happen *instead of* the automatic
clean-up step, not stacked on top of it, or it ends up fighting its own optimizer.

## 8. Finding 7 — there is a *provable* ceiling on how much reordering the x/y comparisons can help, and it's much lower than we need

A related but different idea: instead of touching the scratch qubits at all, what
about reordering the actual comparison gates themselves — the ones that check "is `x`
inside this range?" — so that comparisons needing *different* coordinate wires can
run at the same time? This is a well-known technique from ordinary compiler design
and from real quantum-hardware scheduling: build a graph where each comparison is a
dot, draw a line between any two dots that need even one of the same wire at the same
time, and then **colour** that graph — dots that end up the same colour can safely run
together, because a line between them would have stopped that. (This is the same
family of trick used to speed up preparing a GHZ state by colouring a hardware's
connection map into disjoint pairs of two-qubit gates.)

This is a real, checkable question, so it was checked exactly rather than guessed at.
Every one of the 57 comparison "chunks" that make up the current 10 pieces was listed
along with the *exact* coordinate wires it needs (not just how many — which specific
ones). A graph was built connecting any two chunks sharing a wire, and a standard
graph-colouring algorithm was run on it.

**Result: all 31 of the "is `x` in this range" chunks collide with every single one
of the other 30 — no exceptions.** The best possible grouping still needs 31 separate
turns (mostly working in pairs). That caps any win from reordering these particular
gates at roughly **2x** — nowhere near the improvement needed to approach the
leaderboard.

This isn't a limitation of the search; it's forced by *how ranges are currently
represented*. The technique in use (`plan.md` calls it a **Cube**) always pins down a
number's bits starting from the biggest one. Since almost none of this logo's actual
boundaries (2, 26, 29, 53, 39, 43…) land on a tidy power-of-two boundary, nearly every
single x-range check ends up needing that *same* biggest bit — so all 31 of them are
permanently fighting over the same one or two wires, no matter what order they run in.

**What would change this:** a **comparator** — the alternative already named in
`plan.md` and in the theory below (§12) — checks a number one bit at a time, the way
a person adds two numbers on paper starting from the ones column, rather than reading
every bit simultaneously. At any given moment during a comparator's work, most of its
bits are sitting idle and free for something else to use. Colouring/scheduling only
has real room to help *after* that swap is made — it's the missing ingredient that
made this idea worth trying.

**Update: it was tried.** §11 built a real comparator and raced it against the Cube.
It lost on raw gate count by 2.5-4x, which matters more than the scheduling question
this paragraph raises — see §11 for why that makes the scheduling win moot in
practice (you can't spend a gate-count loss back via depth-only scheduling gains).

## 9. Finding 8 — writing gates by hand (not through Classiq's synthesizer) is not just allowed, it's already how the best result was made, and there's evidence the leaders do the same

Two things were checked directly in the code, not assumed:

**(a) The official checker doesn't care how the circuit was built.** `oracle/verify.py`
reads the *submitted file only* — it checks the file has one register, only `u3`/`cx`
gates, valid qubit indices — and then runs it through a simulator just to confirm the
*answer* is correct. Nothing in that code asks whether Classiq's synthesizer produced
the file. A circuit built gate-by-gate in plain `qiskit` (which is exactly what
`handbuilt.py` already does) is a completely legitimate submission, and it's already
the source of the current best score.

**(b) Classiq's own automatic circuit-building has a lot of built-in overhead for this
kind of problem.** A tiny, nearly-trivial test — "is `x` between 0 and 3, and `y`
between 0 and 3" — was run through Classiq's synthesizer exactly the way the original
baseline notebook does it. Result: **depth 146**, for a single small rectangle with
almost no content. That is *already at the leaderboard's winning depth of 137* — for
one trivial test condition, before the real logo is even considered. This is strong,
concrete evidence that the way Classiq automatically builds boundary-check logic
(`x >= a`) is not efficient enough to get anywhere near the leaderboard, and that the
top scores are very unlikely to have been produced by leaning on that automatic
synthesis. Hand-built gates are the right call — this project is already doing the
right thing there.

**One loose end found along the way:** `reference/submission.qasm` (the file that
would actually be handed in) is still the very first Classiq-baseline circuit
(4373 `u3` / 3502 `cx`, dated Sept 7) — it has not been updated to the much better
1906/1251 hand-built design. This is a small, safe fix worth doing regardless of
anything else in this document.

## 10. Finding 9 — `caterpillar` (the pebbling-based synthesis tool `plan.md` recommended) was installed, built, and actually run — and it's a dead end for this problem

`plan.md` Phase 3 named a specific existing tool, **caterpillar**, as "expected to be
strong... do not treat as fallback." It had never actually been installed or run
before this session. This session fixed that: a real C++ toolchain was built from
scratch (caterpillar + its dependency stack — mockturtle, tweedledum, kitty, lorina —
all real EPFL research-lab code, not a stand-in), verified against a toy example with
a known answer, and then pointed at the real logo problem two different ways.

**What caterpillar does, in plain terms:** feed it a description of the Boolean
function (as a truth table, or as a graph of AND/XOR gates), tell it how many scratch
qubits ("pebbles") you're willing to spend, and it uses a solver to search for a valid
*schedule* — an order of computing and uncomputing pieces — that fits inside that
budget. This is exactly the kind of compute-once-reuse-often scheduling this whole
session tried to hand-design in §5–§7. If it worked, it could plausibly have simply
handed back something close to the leaderboard directly.

**Two attempts, both real, both measured:**

| Attempt | What it fed the tool | Scratch-qubit budgets tried | Result |
|---|---|---:|---|
| A | The logo's full truth table, cleaned up automatically (1282 gates) | 6 through 38 (one budget also given a dedicated 10-minute search) | **Every budget failed** |
| B | A hand-built version mirroring the existing 10-piece design (139 gates — 9x smaller) | 6 through 36 | **Every budget failed** |

The second attempt is the important one. A network 9x smaller than the first still
couldn't find a valid schedule at *any* scratch budget from 6 all the way up to 36 —
on a problem that only has 12 real inputs. If the obstacle were simply "needs a bigger
scratch budget," success should have started appearing somewhere well below 36. It
didn't, at any point in that whole range. That rules out "just give it more scratch"
as the fix and points at the *shape* of the problem instead.

**Why this particular problem is a bad fit for caterpillar:** caterpillar's scheduling
trick works best on **chain-like** computations, where each step mostly depends on
the step right before it (its home use-case is arithmetic circuits like modular
exponentiation, which are naturally chain-shaped). Our function is the opposite shape:
10 independent pieces that all have to be *simultaneously alive* right before the
final XOR combines them. That is a **bushy** computation graph, and a bushy graph
forces many values to stay "pebbled" (kept around) at once, no matter what order you
compute them in. This is the same underlying obstacle already named in §6 (the
"traffic jam" finding) — a different tool, hitting the identical wall.

**Conclusion: caterpillar is being retired as a route for this problem.** Nothing
about the setup was wrong (the toy example matched its documented answer, and the
hand-built network was verified correct against the real logo on all 4096 inputs
before being handed to the solver), and the negative result is a strong one (two
independently-shaped inputs, a 30-level budget sweep on each, one multi-minute
dedicated run) rather than a single quick failure. A few technical variations were
considered and set aside as low-value: a non-solver deterministic scheduling strategy
(would at least give *a* number, but almost certainly a worse one than the existing
hand-built design), and reshaping the network into a narrower chain purely to make it
pebbling-friendly (which would throw away the very parallelism the current design
already exploits). None of these change the underlying diagnosis, so none were run.

## 11. Finding 10 — the comparator idea was actually built and raced against the Cube, and it lost, decisively, on raw gate count

§8 and §10 both pointed at the same untried idea: replace the current "fix several
bits at once" range check (a **Cube**) with a **comparator** — a chain that checks a
number one bit at a time, the way a person compares two numbers digit by digit. The
theory was that this would let different comparisons interleave instead of colliding,
loosening the scheduling ceiling found in §8. This session finally built one and
raced it, head to head, against the existing Cube machinery, on two real ranges from
the logo:

| Range | Shape | Cube: depth / CX | Comparator: depth / CX |
|---|---|---:|---:|
| x in [2, 26] | wide (25 values), unaligned | **81 / 50** | 215 / 131 |
| y in [39, 43] | narrow (5 values), unaligned | **61 / 36** | 149 / 89 |

Both circuits were verified bit-for-bit correct (all 64 inputs, exact statevector
check) before trusting these numbers, and the comparator was already given its one
legitimate optimization — the same relative-phase ("Margolus") Toffoli trick §5 and
`handbuilt.py` already rely on elsewhere, applied under the identical safety rule
(a scratch qubit is used only as a *control* after being set, and is later undone by
running the exact same gate sequence backward). That optimization alone cut the
comparator's cost by roughly 3x (from a first, unoptimized 621/398 and 574/372) — and
it *still* lost to the Cube by **2.5–4x**, on both a wide range and a narrow, ragged
one that should have been the comparator's best case.

**Why it loses:** the Cube approach isn't naive — `best_blocks()` doesn't just chop
a range into aligned chunks, it also checks whether the *complement* (the gap outside
the range) is cheaper to describe, and picks whichever is smaller. For most real
ranges this collapses the whole thing into just 2-4 gates. A bit-serial comparator, by
contrast, always needs to examine *every* bit of *both* endpoints (12 small steps for
a 6-bit register, twice — once to test the lower bound, once for the upper), and each
of those two passes needs its own scratch chain computed *and* uncomputed. That's a
close-to-fixed cost that doesn't shrink just because a range happens to be easy to
describe, and it turns out that fixed cost is already bigger than almost anything the
Cube approach produces.

**Why this matters beyond just one lost race:** reordering/scheduling tricks (§8) can
only ever change *depth*, by letting independent things happen at the same time — they
cannot reduce the *total number of gates* in the circuit. Since a comparator-based
piece costs 2.5-4x more gates than a Cube-based piece for the exact same range, simply
swapping every piece in the current 1251-CX design over to comparators would make the
CX count *worse*, not better — potentially into the 3000-5000 range — no matter how
well the scheduling problem is solved afterward. The leaderboard needs *both* depth
**and** CX to come down (137 / 561). A change that can only help one of those two
numbers, while actively hurting the other, is not the fix being looked for here.

**This substantially weakens (though doesn't fully rule out) the theory in §12 below.**
It's still possible a *smarter, non-textbook* comparator construction exists — one
comparison pass instead of two, or an amortized ancilla scheme that avoids repeating
the uncompute cost — but the plain, standard version of the idea, implemented and
measured rather than assumed, is a loss. Anyone revisiting this should treat "a
comparator will obviously be cheaper" as disproven for this problem, not as a
starting assumption.

## 12. A theory of what the top submissions (137 depth / 561 CX) are actually doing

This is an educated guess built from the evidence above — nobody has seen their code —
but it is not a wild guess. **Point 3 below was the session's leading theory going in,
and §11 has since tested and weakened it — the honest updated picture follows.**

1. **They are not using Classiq's automatic comparator synthesis** (§9b makes this
   very likely).
2. **They probably aren't using more compact "logical" pieces than we found** — the
   rank-10 result (§2) says our piece *count* is already minimal for this style of
   decomposition, and a 137-deep, 561-CX circuit has a similar total "gate budget" to
   ours (both are in the same ballpark once you divide total gates by 18 wires).
3. ~~The real difference is the *shape* of the gates — a bit-by-bit comparator instead
   of our all-at-once Cube.~~ **§11 built this and measured it: the standard,
   textbook version of a comparator costs 2.5-4x *more* raw gates than the Cube
   approach already in use, on both an easy and a hard real range from the logo.**
   Since reordering/scheduling can only ever change *depth* (by overlapping
   independent work), never the total gate count, a straight swap to comparators
   would make CX worse across the board — the wrong direction, since the leaderboard
   needs CX to drop from 1251 to 561, not rise. This doesn't prove no comparator-style
   idea can ever help (a smarter, non-textbook construction is still conceivable — see
   §11's closing paragraph) but it rules out "just switch to comparators" as a
   plug-in fix, which is what this theory originally proposed.
4. **All top entries use the full 18-qubit width.** That's consistent with using
   several ancillas as *independent* running totals for different comparisons at
   once, rather than one shared flag qubit doing all the work — the opposite of our
   current design's structure. **This part of the theory is still untested and still
   plausible** — it doesn't depend on point 3 having been right.

**Where this leaves the theory as a whole:** the leaders are still very unlikely to be
leaning on Classiq's automatic synthesis (point 1 stands on its own evidence), and the
"many independent parallel flags" structural idea (point 4) is untouched by §11's
result. What's no longer credible is the specific mechanism ("swap Cubes for plain
comparators") this session guessed at for *how* that parallelism gets built. The real
mechanism is still an open question — see §13.1.

## 13. Concrete next routes, in priority order

### 13.1 — Revisit the "aligned-bound cover" idea from `plan.md` Phase 2

`plan.md` flagged, on 2026-09-13, that snapping a rectangle's edges to the nearest
power of two is "cheap, untried, and the arithmetic says it could be large" — worth up
to ~100 depth per boundary. Only 4 small calibration probes of this idea exist in the
log; it was never tried as a full replacement for the whole logo's cover. Unlike the
comparator idea (§11, now closed), this stays *within* the Cube approach that's
already known to be gate-cheap — it doesn't carry the same "total gates go up" risk.
This is now the most promising untried route.

### 13.2 — If revisiting the comparator idea at all, look for a genuinely cheaper construction first — don't re-run the same one

§11's result was specifically about the *standard, two-independent-passes* bit-serial
comparator. It does not rule out a construction that, say, checks both bounds in a
single combined pass instead of two separate compute/uncompute cycles, or reuses
scratch qubits between bit-positions instead of allocating a fresh one per bit (this
would shrink the *qubit count*, though probably not the *gate count*, which is the
metric that actually lost the race). Anyone picking this back up should design and
verify a specific new construction and race it the same way §11 did — not assume the
theory was merely "unlucky" on the first try.

### 13.3 — Reopen the question of what the leaders' structural trick actually is

§12 point 4 (full 18-qubit width, independent parallel flags) is the one part of the
original theory that survived §11 untouched. It's still just a guess. Worth spending
real time on this before building anything else: what circuit *shape*, other than
"many small comparators," would use every qubit as an independent running total?

### 13.4 — Housekeeping (small, no risk)

Update `reference/submission.qasm` to the current best verified circuit (1906/1251)
instead of the stale original baseline (§9, last paragraph) — whatever else happens,
the file that would actually be submitted should reflect the best result already in
hand.

## 15. Addendum, 2026-09-16 — the disk sub-problem, tested exhaustively

The user pushed back on §12's theory with a sharp, correct objection: "a disk is not
really a term, it's a union of smaller terms — didn't we already find that even a
handful of rectangles costs more depth than the whole leaderboard budget?" That
objection turned out to be right, and testing it thoroughly is what this section
records. `plan.md`'s Phase 3 table now has the same numbers — this section is the
plain-language version of that update.

**Every disk-building technique tested lands in the same 250-1400 range for one
disk — none of them are remotely close to competitive:**

| Technique (Disk 1, ~225-229 px) | Depth | CX |
|---|---:|---:|
| Row-staircase (naive rectangles, the "obvious" idea) | 1167 | 806 |
| GF(2) rank-decomposed (same technique that found the whole logo's rank-10) | 949 | 616 |
| Octagon + hand-built adder arithmetic (Strategy E) | 1361 | 967 |
| Bounding-box + real multi-level minimizer (Strategy D, `mockturtle`) | not built — ruled out analytically: 248 AND gates is already a ~750 CX floor | |
| **The leaderboard's *entire* circuit, for all four shapes combined** | **137** | **561** |

Two builds here are real, substantial pieces of work, not quick checks:

**The octagon (Strategy E)** is the one idea from `plan.md` that's genuinely
different in kind from "sum of rectangle-shaped terms" — a disk, cut into a square
intersected with a diamond, where the diamond is built by rotating coordinates
(`u=x+y`, `v=x-y`) so the diagonal cut becomes an ordinary range check. This needed a
real reversible adder, built and verified bit-by-bit against brute-force addition
before anything was built on top of it (the riskiest part first, on purpose), then a
comparator on the result, done twice (once per rotated coordinate), plus the cheap
bounding-box checks, plus a 4-way AND — all built, all verified correct on every one
of the 4096 possible (x,y) inputs, all optimized with the same relative-phase-Toffoli
trick used everywhere else in this project. It still lost to simply using more
rectangle terms. The reason: two adders and four comparators are each individually
expensive (a single comparator alone costs 150+ depth, per §11), and the octagon
needs all of them — there's no version of "add adders" that comes out cheap here.

**Strategy D** handed the disk's own reduced local truth table (shrunk from 12
variables to a genuine 10, via the bounding-box trick) to `mockturtle` — the actual,
real, state-of-the-art multi-level logic minimizer this whole project's tooling was
built around — and let it do its best. Even so, it came back with 248 AND gates.
Since each AND needs at least one Toffoli-equivalent gate (3 CX at best), that's a
hard floor of ~750 CX before even converting the result into an ancilla-respecting
reversible circuit — which, given the earlier caterpillar finding (§10), would likely
add more gates back in through unavoidable recomputation, not fewer.

**What this collectively means:** five structurally different techniques — naive
rectangles, rank-optimal rectangles, non-separable arithmetic, and a real external
multi-level minimizer — were each given a genuine, careful attempt, on the same
sub-problem, and all five landed in the same expensive range. That consistency is
itself the finding. It's no longer credible that "the right predicate style for a
disk" is the missing piece — every predicate style tried is expensive, including the
ones that are supposed to be "the correct way" to build a circle. The bottleneck
looks structural to the whole *approach* (isolate a shape as its own sub-circuit,
build it, XOR it into the design), not to any specific technique within that
approach. §12's theory got that fresh look in the follow-up conversation: a real
depth/CX ratio comparison (leaders run at ~46% of the theoretical max gates-per-layer,
we run at ~17%) plus a literature check (graph-coloring for depth is real and
published, but only schedules gates already chosen — it can't create parallelism
between gates forced to share a qubit; the generic parity/Walsh-basis synthesis is a
confirmed dead end, needing depth ~2¹² for a dense 12-qubit diagonal with no ancilla).
That work is now written up as `plan.md` Phase 3.5 ("Disjoint-qubit redesign"),
not repeated here — see that document for the concrete task list. **Update,
2026-09-16, later the same day: Phase 3.5's own first task (check feasibility before
building) closed it negative.** Per-bit sensitivity of the real target function
(computed directly, cross-checked against the Walsh spectrum in §12) shows `y5`
changes the answer 53.1% of the time, `y4` 38.4%, `x5` 33.8% — these bits are
essential to most of the grid, not droppable, so most terms in *any* decomposition
must read them and are then forced to serialize on that shared qubit. The
disjoint-qubit-sets bet does not pay off here. See `plan.md` Phase 3.5 for the full
writeup — as of this update, no candidate theory for the leaders' technique remains
standing.
